# pdt-en

**Put a software team inside an agent session.**

> This is the **English edition** of the PDT group skill family. The Chinese original lives at [aragornpangit/pdt-group](https://github.com/aragornpangit/pdt-group); structure, roles and rules are identical, only the language differs.

PDT group is a **role skill family**: one first-level department plus four second-level departments, 4 installable roles in total (pm / dm / tm / scoutM), plus one class of subagents generated dynamically on dispatch (`de` / `te`) and two kinds of on-demand derived subagents (pm's `pde`, scoutM's `se`). Each manager role is a `SKILL.md` that an agent can load, each running in its own session and collaborating over herdr messages, so the chain "user requirement → SPEC → vertical-slice implementation → independent verification" runs end to end; scoutM is the manager of the Reconnaissance department, taking on technology selection and pre-refactor research.

It is not a tool skill but **an organizational protocol**: it defines who reports to whom, which directory artifacts land in, and which words go over which channel.

> The methodological skeleton of this project is built on [Matt Pocock](https://github.com/mattpocock)'s open-source skill set. We explicitly reference several of his skills and have learned a great deal from them. The item-by-item list and what we gained are in **[ACKNOWLEDGMENTS.md](ACKNOWLEDGMENTS.md)**.

## About this release mirror

**This repo is a release mirror, not the only place where writing happens.**

- **Source of truth**: the `pdt-group` bucket in the author's skill container repo `Skills` (internal private repo `userid/Skills`, not public). Role definitions, group conventions and the ledger are maintained there.
- **Sync direction**: one-way, container repo → this repo. Changes land in the container repo first, then sync here for release.
- **Purpose of this repo**: external distribution and reading. You may freely fork and modify it (MIT), but this repo **does not accept** backflow of direct changes; edits made here are overwritten on the next sync.
- **When the two disagree**: the container repo wins; if you can only read this repo, take this repo's current snapshot as authoritative.

The role directory structure preserved on sync is "one directory per role, placed directly at the repo root", identical to the flattened result of `skills/pdt-group/<role>/` in the container repo.

## Roles and subagents

| Role | Level | Responsibility |
|---|---|---|
| [`pm`](pm/SKILL.md) | Group entry + manager | Product manager and group lead: the group's only user entry, forms and manages the dm/tm sessions, cross-department coordination and top-level arbitration; writes the SPEC itself (80-line baseline, covering what/why and how), arbitrates development/test reports. May derive subagents on demand (they report only to pm, pm consolidates the results); zero document output at group level |
| [`dm`](dm/SKILL.md) | Manager | Development manager. Sets design decisions and slicing conventions (writes the plan and progress itself, 50-line baseline), derives n `de` dynamically once work reaches the dispatch stage, reviews and merges |
| [`tm`](tm/SKILL.md) | Manager | Test manager. Designs cases and conclusions (writes the test report itself, 40-line baseline), derives n `te` dynamically once work reaches the dispatch stage, reviews and sends back defects |
| [`scoutM`](scoutM/SKILL.md) | Department manager | Reconnaissance department manager. Takes technology selection, competitor analysis, pre-refactor research: first interrogates the performance/maintainability preference, then evaluates the codebase internally and benchmarks 2-3 open-source references externally, producing an architecture Spec under `docs/scout/`; dispatches several se on demand |

**Dynamic subagents** (no skill files installed, generated by managers from dispatch prompt templates):

- `pde` × n: product requirement conversations / evidence gathering / verification. Holds the five upstream skills `grill-me`, `grilling`, `grill-with-docs`, `research` and `to-spec`, and talks to the user about product requirements (the addresses are written into the dispatch prompt by PM)
- `de` × n: development engineer. Inside the git worktree pre-created by DM: implement → tdd → self-review → commit (template in [`dm/templates.md`](dm/templates.md))
- `te` × n: test engineer. Executes cases, holds `code-review` and `diagnosing-bugs` (template in [`tm/templates.md`](tm/templates.md))
- `se` × n: scout-engineer (scout). Splits research into sub-questions, scans the codebase inward and benchmarks open-source references outward; holds the `research` skill, passed in by ScoutM in the dispatch prompt (template in [`scoutM/templates.md`](scoutM/templates.md))

## How a requirement runs to completion

A requirement enters at pm and flows one-way along pd → dev → test; `{seq}` is the anchor spanning the whole chain (generated by pm when it creates the SPEC, reused by the development plan and the test report):

1. **pd**: `grilling` interrogates and converges the decision → pm gathers evidence itself (reads source, reports, config) → pm writes the SPEC itself
2. **dev**: DM sets design decisions (written to `docs/dev/plan/{seq}-devPlan-{semantic-slug}-{YYMMDD-HHMM}-v1.md`) and slices vertically by tracer bullet → derives n `de` as appropriate, each implementing inside its worktree, running the tdd red-green loop, self-reviewing on the Standards axis, committing in its branch → DM reviews and merges
3. **test**: tm designs by the five case classes (written straight into the report) → derives n `te` to run in parallel → after review, tm sends to both pm and dm over herdr

Research branch: if the pd or dev stage hits technology selection, competitor benchmarking, or pre-refactor assessment, pm / dm dispatches scoutM to research, the architecture Spec lands in `docs/scout/`, and the conclusion flows back into the SPEC or the development plan in one sentence.

## Installation

Copy the 4 role directories **flattened** into the harness skill directory, with no nesting (`de` / `te` are not installed; dm / tm derive them dynamically):

```bash
for d in pm dm tm scoutM; do
  cp -r "$d" ~/.agents/skills/
done
```

`pdt-group` is a complete team; it only makes sense when **all of it is installed** (the roles have dispatch dependencies on each other). Replace `~/.agents/skills` with the skill directory of your harness.
