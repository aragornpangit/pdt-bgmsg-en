# Dispatch and wrap-up disciplines (DM, full text of 20 items)

> Single carrier of the full text; [`SKILL.md`](SKILL.md) keeps only a pointer and a three-item high-risk summary. For clauses marked "team discipline #N" the single full text is in the "Team disciplines" table of [`../pm/group-conventions.md`](../pm/group-conventions.md); this file keeps only the DM execution surface.
> The three-part kit for each discipline (clause + companion action + reason) and the admission threshold are in the "Team disciplines" table header of group-conventions; this file does not restate them.

Items 1, 2, 6, the "four steps before commit" of item 5 and the reporting requirement of item 4 are already built into the "de dispatch prompt template", verify item by item when changing the template; of these, item 2's `context: "fresh"` and item 8's `timeoutMs` are **dispatch parameters** (written on the call), listed explicitly in the template's "dispatch parameters" section and in one body line, check them together when changing the template; the check actions of items 3 and 7 are performed by DM personally. In dispatch situations that do not use the template, the prompt must carry the applicable clauses.

1. **Role anchoring**: the first paragraph of the prompt states "you are de, not DM; you have no subagent tool and must not dispatch subagents"; when dispatch is needed, only write "suggest DM dispatch X"
2. **Fresh dispatch**: explicit `context: "fresh"` (does not inherit the parent conversation), the prompt is fully self-contained; the worktree is pre-created by DM and stated as "already exists, cd into it directly"
3. **Check the old run before re-dispatching**: confirm the old run has terminated before re-dispatching, never reuse a running worktree (one writer per cwd); query running status non-blockingly through the task status interface, do not rely on waiting
4. **Reporting is a message**: require the subagent to reply to DM directly in the reporting format, do not save a separate document file; a truncated report does not mean the work is incomplete, check the commit and artifacts before judging
5. **Main worktree discipline**: the shared main worktree is only for reads and new commits, amend/reset/rebase only in your own worktree; four steps before a subagent commits (written into the prompt): `git log -1` to check the base -> if HEAD has advanced, `git diff <base>..HEAD -- this ticket's files` (non-empty means stop and report) -> explicit-path `git add` (no `-A`) -> never amend/reset someone else's commit. **Commit boundary (team discipline #1)**: new files (untracked) must be `git add`ed first, otherwise `git commit -- <path>` reports `pathspec ... did not match` and commits nothing. **Worktree absolute path discipline**: **every path given in a ticket carries the worktree absolute path prefix**, and states "once the worktree is created, all edits and commands use that absolute path; writing any file or committing anything in the main repo worktree is strictly forbidden". **Companion actions**: (1) the first paragraph of the ticket states the worktree absolute path clearly (including the full prefix of the in-project subpath); (2) the ticket states **mis-write handling** = "move the change into the worktree immediately + restore only the files **you touched** in the main repo + paste `git status` of both the main repo and the worktree for review + report back"; (3) self-check before dispatch: **does every path appearing in the ticket carry the worktree prefix** (if not => add it). **Reason**: when the ticket gives repo-relative paths, subagents edit in the main repo as a matter of course; two de in a row landed changes in the shared main repo => risk = **the change gets swept into another ticket's commit**, or **the restore destroys someone else's uncommitted change**. The root cause is the dispatch template, not the individual. **Incidental registration**: if an out-of-bounds check script asserts "`git status` must be empty", on the **shared main repo** it will **false red** because of **other people's untracked files** => **such checks must use "self-a... [truncated]
6. **Unique numbering**: ticket numbers are assigned and made unique by DM at dispatch time (check against the plan and running tickets); if a subagent finds a conflict, stop and ask
7. **Citation means taking from source (team disciplines #7 / #4 / #5 / #9)**: DM execution surface = before dispatching, run a literal grep on every referenced SPEC / criterion item and paste the hit line into the ticket (if you cannot produce the line the citation does not count, writing from memory or from compressed context is forbidden); verification runs `grep -c` only on the substring echoed by the written script, never hand-retype the pattern string; report counts with scope; third-party weights and restricted-license artifacts are barred from the repo, compliance belongs to PM
8. **Timeout mandatory (team discipline #6)**: DM execution surface = fill in `timeoutMs` when writing the ticket/prompt (device / long chains >= 45 min and report in segments, pure document tickets may be short). **Reason** = when the default timeout hits, the long task still running is silently killed, all prior work is wasted and nobody knows
9. **Acceptance review must declare the reviewed version (team discipline #8)**: DM execution surface = when diffing, checking contracts or numbers on de output / other parties' documents, the conclusion carries the reviewed object's commit SHA / three elements; "left trace vs leftover" = old literals are explicitly marked "obsolete / superseded"
10. **A change that affects downstream consumers => must check downstream and keep a comparison**: **whenever a change "affects downstream consumers" in behavior (orientation / geometry / size / key semantics), check downstream and keep a comparison; the acceptance items of such tickets must include "the downstream consumer's visible result is still normal"**. **Companion action**: the acceptance checklist must be able to point at that "downstream visible result" item; if it is missing the acceptance is considered incomplete. **Reason**: after the upstream behavior change landed, a downstream hard-coded assumption was exposed and the downstream output was silently dropped, while the upstream acceptance checklist had no "is the downstream result still normal" item => nobody caught the regression until the user reported "the feature is gone"
11. **Transform the input before processing => must prove equivalence, or only try after failure**: whenever input is transformed (upscale / rotate / invert / binarize etc.) before parsing or processing, **if the transform can act on input that "would have succeeded anyway" => you must first prove "the transformed result" equals "the pre-transform result"**; if you cannot prove it => it may only be wired in as "**try only after everything before it has failed**" (**structurally guaranteed not to overwrite results that already succeeded**). **Companion actions**: (1) the dispatch states which of the two wiring modes is used (try only on failure / provide byte-identical evidence first), where the evidence = sha256 comparison of both arms' results with an inconsistency count of 0; (2) add a **counter-arm**: make the transform preferred / parallel => it must error or measure an inconsistency (no teeth does not count); (3) the acceptance checklist must contain this item. **Reason**: measured, the seemingly harmless "upscale" transform made a considerable share of samples that could originally be solved read out different results => **a transform is not harmless**
12. **A check must be bound to its own conditions: neither "red because of others" (false red) nor "green because of absence" (false green)**: **for any gate/check script, red and green may only be determined by "the property of the object under check itself"**, external conditions must not be used as criteria ((1) other people's untracked files turn the out-of-bounds check red; (2) input material missing, the directory exists but holds 0 files, so the check prints "all pass"). **Companion actions**: (1) out-of-bounds/scope checks always use **"self-anchored baseline + explicit allowlist"**, **requiring "the whole repo's `git status` is empty" is forbidden**; (2) material/input checks **must first judge "does the input exist, is the count > 0"**, if missing then `rc!=0` and print the gap (fail-loud), **must not take the "empty set => no failure => all pass" path**; (3) **the negative arm must cover both directions**: drop in one outsider untracked file => must still PASS (proves the false red is fixed); touch one file on the forbidden surface => must FAIL (proves the teeth are still there); empty input => `rc!=0`, input present => normal verdict. **Reason**: when the check result is decoupled from its own conditions => false red wastes human effort, false green lets defects through, both directions make people **believe a wrong conclusion**
13. **Verify the final artifact, not just the source**: correct source != correct build artifact (resource merging, variants, build-time optimization can all change the result), and whether such changes are right can only be seen **on the installed / built thing**. **Companion actions**: (1) the ticket requires pasting **artifact-side** verification output (packaged properties, build artifact listing etc.); (2) add a **static check script + negative arm** (break a property => must go red)
14. **When a ruling conflicts with the implementation, "intent takes precedence over the literal" + the difference must be flagged proactively**: if the implementer finds that **following the ruling literally would violate a harder purpose clause in the ruling** => **implement by purpose + proactively flag the difference + give the cost and the way to revert**, and the arbiter decides; **both of these are forbidden**: **silently following the literal** (breaking the purpose), **silently changing it** (discovered only afterwards). **Companion action**: the ticket states "when conflicting with the ruling/SPEC literal: implement by purpose and flag the difference and cost in the first paragraph of the report, or stop and report back", **and acceptance lists "was the difference flagged proactively" as a check item**. **Reason**: the **purpose** of a ruling is the real constraint, the literal was only the best expression at the time; binding the two together prevents both "mechanical execution" and "unauthorized rerouting". **The gate itself must also have teeth**: **when running a gate, do not swallow the return code through a pipe** (the rc in `check.sh | tail -1 && git commit` is `tail`'s **0**) => **always `set -o pipefail` or put an explicit `rc=$?` into the conditional branch**
15. **Localize the fault by layer before judging, do not thrash on the wrong layer**: **companion action = fixed four-step evidence gathering, no skipping and random trying**: (1) **near side**: check whether the listening port is LISTEN, whether there are zombie connections, whether there are leftover tunnel processes; (2) **cross validation**: open a separate independent channel to see whether the target is reachable; (3) **far side**: ask the target end once directly (**it answers but the list is empty => the channel is up, there is nothing on that end**); (4) **judge**: **fix what the near side can fix**, for **what needs a human, state clearly "what a human must do at that machine" and escalate to PM**. **Forbidden**: repeatedly restarting the same service, changing environment variables, switching to other paths and trying hard. **Reason**: after the remote device dropped, layered evidence gave "the channel is still up, but the far-end list is empty" => **immediately judged as "there is no device on that side, a human is needed"**, avoiding repeated thrashing on the near side
16. **The per-item records a conclusion depends on must be exported and committed before large artifacts are cleaned up**: **keeping only the summary = the conclusion cannot be recomputed independently** (the reviewer cannot accept it). **Companion actions**: (1) at the end of collection **automatically** export a slim table (**keep only the columns required for recomputation**, record "count + hash", **do not** store raw snapshots/images); (2) also provide a **recompute script** (reads only the slim table, outputs all conventions by default) and a **machine check** (e.g. the verdict must be identical in two files, the sample count must be labeled, the slim table exists and can be recomputed); (3) **run the export through before cleanup**, if it cannot export => **prompt "do not clean the large artifacts yet" and abort the cleanup**; (4) **negative arm**: delete the slim table => **must error** and prompt "the conclusion cannot be recomputed independently". **Reason**: at wrap-up thousands of per-item snapshots were deleted => the reviewer could not independently recompute the headline number and could only judge FAIL; after adding the slim table the reviewer recomputed with **their own logic** and got **item-by-item agreement** => once mechanized this kind of rework stops happening. **Same family**: shares its origin with "gate probes must be committed to the repo" and "the evidence standard is not lowered because the cost is low"
17. **A property anchor is only for "pointing", not for "taking the set"; naming must not collide with your own machine check**: **(a) anchor boundary**: when referencing an entity across artifacts use a **stable property anchor** (e.g. the value range of some intrinsic property) to avoid "different numbers per artifact => cross-contamination"; **but an anchor is only a summary** => **to extract the member set precisely you must still recompute by definition**, **do not filter using the anchor's range**. **Companion actions**: when citing an anchor **state that it is a summary**; anywhere a "set must be taken" **always recompute by the defining algorithm** and give the recompute command; **negative arm**: filter by anchor vs recompute by definition, when they disagree **the recomputation wins** and the difference is recorded. **(b) naming colliding with the machine check**: **file names/paths must not contain "keywords that your own machine check will hit"** (otherwise the check **hits itself** and produces a false red). **Companion actions**: before naming, **run your own machine check once**; design the machine check to **distinguish "file name" from "file content"**. **Reason**: both groups are the same family as item 12, "the check/reference is decoupled from its own conditions", only this time the invisibility cloak is **naming** and **summary**
18. **Tickets containing parallel / multi-process experiments must carry the hardening checklist**: for any dispatch containing parallel or multi-process experiments (host or device), the ticket **must** state three things: (1) **create child processes with `spawn` semantics, `fork` is forbidden** (after the parent has run a compute-library forward pass or started threads, a fork makes the child **silently deadlock**); (2) **hard-wrap every combination in `timeout`**, with `terminate / join / kill` fallbacks; (3) **write results incrementally line by line to disk** (so a hang does not lose all results). **Liveness criterion** = the process CPU share (often `< 5%` when hung) + stalled output mtime; **do not** judge a long run by "no output" alone
19. **Tickets that rename/move files must actually run "the checks that depend on them" before wrap-up**: **whenever a ticket contains `git mv` / rename / move / delete of a file => before wrap-up you must run the checks that depend on those paths once, for real** (checks with hard-coded paths in scripts, gates that key off the file name, assertions that read that file ...), **and leave a trace**. **Companion actions**: (1) the dispatch states "after renaming, list the dependent checks item by item and actually run them"; (2) after renaming, first `rg` the places **referencing the old path** (including scripts, README, gates) and **handle each one** (change it / register it as an exception); (3) **prove the breakage found is fixed with a negative arm** (temporarily change the checked object back => FAIL must reproduce); (4) **if it is genuinely an exception on another ticket's forbidden surface** => **revert it after the change and register the old name as "not changed"**. **Reason**: `git mv`ing three reports to semantic names **broke three real checks**, one of which went from "can catch a report being edited" to `git diff` always empty => **permanently false green** (same family as item 12); **DM only missed nothing after the whole investigation was done** => showing that "remember to check" is unreliable and must become "this item is on the wrap-up checklist of a rename ticket"
20. **Commit identity gate (team discipline #10)**: **the author/committer name of every commit (including merge) must carry the role label**, always via `git -c user.name='userid(dm)' -c user.email='userid@example.com' commit …`; **document commits put "writing role + ticket id" on the first line of the message**. **Self-check command (run once before touching the gate / wrapping up)**: `git config --show-origin --get core.hooksPath` => must be an **absolute path** whose directory exists (a relative path resolves inside a worktree to a non-existent `<worktree>/.githooks` => the hook never runs and the gate is decoration). **Three blind spots**: (1) the hook once did not run at all inside worktrees, same root cause; after switching to an absolute path, re-verify end to end (illegal identity rejected with rc=1 / legal one passes); (2) `git merge` does not trigger pre-commit (`commit-msg` covers merges as a fallback, but still pass `-c` explicitly and pass the gate in one go rather than relying on the fallback); (3) `--no-verify` is forbidden for the identity gate. **`de` is not exempt today**: if the global `includeIf` is not installed, a de commit must pass `-c user.name='userid(dm)'` by hand; once installed, still use the self-check command above to confirm the gate is alive.
